# Current app assessment — 2026-10-02

## Scope and conclusion

Assessed the current working tree, including its uncommitted live-camera implementation. Used ECC codebase-onboarding for architecture mapping and production-audit for evidence and failure analysis. No application code was changed. The ECC repo-scan entry is an installation bootstrap, not an available scanner; its installer was not needed. The fix-defect workflow was not applied because this task requests diagnosis.

The symptoms have several concrete implementation causes. Camera transcription is a sequence of independent batch jobs with a result-discard race; the display combines two unrelated recognition engines; active-speaker evidence loses visual temporal resolution; and the body highlight is a heuristic rectangle displayed at an old location. There is no silhouette segmentation or visual-to-text lip-reading model.

Confirmed source behavior is distinguished below from hypotheses requiring a representative camera recording. Actual live latency and transcription word error rate were not measured.

## Project map

Python package `src`, Python >=3.12,<3.15, managed with uv. Browser UI is inline HTML/CSS/JavaScript generated by Python. The server uses the standard-library ThreadingHTTPServer. There is no database, frontend build system, or persistent live-session store.

### Actual live path

1. Browser obtains microphone/camera with `getUserMedia` and shows the live stream.
2. An optional browser SpeechRecognition instance writes provisional `liveText` independently.
3. MediaRecorder stops every two seconds, sends a complete recording, and starts a new recorder.
4. Server rejects the upload with 429 if another inference holds its single service lock.
5. Accepted recording is written to disk, re-encoded to H.264/AAC, then converted to PCM audio.
6. Shared recognizer probes/decodes video, transcribes with Whisper, detects/tracks faces, stabilizes track IDs, scores Light-ASD, then associates captions. These stages execute sequentially.
7. Server returns clip-relative times, face/body boxes and captions as one response.
8. Browser accepts only the latest submitted clip number; accepted events all appear immediately, with one historical box per event, until a processing-time expiry.

### Actual offline path

`src.main` extracts audio and calls the same recognizer, enabling word timestamps and ECAPA clustering. It writes speech/faces/events JSON, VTT, annotated MP4 and a review page. Offline rendering interpolates boxes against video presentation time, unlike the live UI.

| Setting | Camera | Offline |
| --- | --- | --- |
| Default Whisper model | base | large-v3 |
| Input context | Independent two-second clips | Whole input passed to Whisper |
| Word alignment | Disabled; segment text stored as a Word | Enabled |
| Voice clustering | Skipped | ECAPA per Whisper segment |
| Identity | Face-track position continuity | Voice cluster plus face track |
| Activity candidate cap | 4 tracks | 8 tracks |
| Minimum face track | 2 detections, no duration minimum | 15 detections and 3 seconds |
| Display clock | Response arrival plus expiry | Video presentation timestamps |

## Findings

### 1. Completed camera transcripts can be discarded indefinitely under sustained load — confirmed, highest priority

References: `src/live.py:57`, `src/live_view.py:102`, `src/live_view.py:112`, `src/live_view.py:126`.

Every submission increments `chunkNumber`. Concurrent work is rejected by the server. A successful response is discarded unless its number still equals `chunkNumber`, even if all newer requests failed.

Example: clip 1 is uploaded at t=2 s. At t=4 s clip 2 increments the number and receives 429 because clip 1 is still running. Clip 1 finishes at t=5 s and the browser discards its valid transcript. Repeating inference times longer than the capture cadence can prevent any local results from appearing during continuous capture. Rejected recordings are not retried or retained.

A deterministic execution of the actual JavaScript `recognize()` function confirmed zero displayed results after advancing the submission number before resolving the first response. This proves the discard logic, not the user's actual inference duration.

For an accepted result, speech-to-display delay is approximately remaining capture-window time + upload + normalization + decoding + Whisper + face analysis + Light-ASD + response/render time. No stage timings or latency budget are recorded. Simply increasing the model size may worsen this failure mode.

### 2. Transcription has fragmented context and two competing text sources — confirmed mechanisms; accuracy impact needs measurement

References: `src/live.py:27`, `src/speech.py:50`, `src/main.py:118`, `src/live_view.py:91`, `src/live_view.py:113`.

- Camera defaults to base; offline defaults to large-v3. Offline quality advice does not describe the camera default.
- Each clip is transcribed independently with no cross-clip prompt/context, overlap reconciliation or application-level voice-activity endpointing. Fixed cuts can split words and sentences. Recorder restart gaps are an additional possibility, not measured here.
- Camera disables word timestamps; fallback Word objects contain whole segment strings. Fine-grained reassignment inside a segment is unavailable.
- Browser recognition and local Whisper never reconcile text. Attributed events replace the browser text while active; afterwards the last `liveText` returns. Browser final/interim flags are not used to build a committed transcript, and only local events are appended to the transcript panel.
- The application passes an explicit language and `task="transcribe"`; accidental translation is not supported as the leading explanation. Browser locale can still choose a language different from the speech.
- Local transcription receives audio only. Visual mouth evidence affects speaker attribution, not the decoded words.

### 3. The app cannot identify a silhouette — confirmed missing capability

References: `src/vision.py:187`, `src/render.py:252`, `src/live_view.py:89`.

`body_box()` expands the face to three times its width and four times its height, offsets the top and clips to the frame. The UI draws a rectangular button. There is no body detector, pose model, instance mask or contour extraction. A faithful silhouette requires an additional segmentation capability and association of its person mask with the speaking face.

### 4. Live highlights use stale positions and can disappear at clip boundaries — confirmed

References: `src/live_view.py:75`, `src/live_view.py:82`, `src/live_view.py:108`, `src/media.py:201`.

The browser chooses `boxAt(track, event.end)` once upon response and freezes it for the display duration. It never tracks the person in current preview frames. Even a correct historical attribution therefore drifts when the person moves.

Every event in a response is displayed together, with the same expiry, ignoring their relative start/end times. Sequential turns can consequently appear simultaneous; multiple segments for the same person can create duplicate overlays.

`boxAt` rejects timestamps beyond `track.end + 0.04`. Retaining every fifth frame means a 25 fps two-second clip may have its last detected sample at 1.8 s. Speech ending at 2.0 s then returns a null box. Executing the actual function with these inputs reproduced this disappearance.

Times in the transcript remain clip-relative; no session offset is added. Results and labels are not isolated by capture session. Server identity maps and lock are shared across clients, and browser response acceptance uses clip numbers without a capture-generation check.

### 5. Active-speaker scoring receives reduced motion evidence — confirmed preprocessing; magnitude unmeasured

References: `src/media.py:170`, `src/light_asd.py:203`, `src/light_asd.py:225`.

Only every fifth decoded image is retained: 5 fps for a 25 fps input, 6 fps for 30 fps. Light-ASD builds a 25 fps face sequence by choosing the nearest retained image while interpolating boxes. Repeating images cannot recover the missing mouth motion; interpolated crops can also move over a repeated image. This is a plausible source of weak or incorrect audio/visual matching, requiring comparison against genuine consecutive frames to quantify.

The four/eight-track cap is global to each input clip/video and ranked by summed face area over detections, favoring larger and longer tracks. It is not a per-timestamp candidate limit. Later offline shots can therefore have visible faces that were never scored. Missing scores are treated as off-screen even when an unscored face exists.

### 6. Speaker identity and turn boundaries are weaker than the interface suggests — confirmed

References: `src/live.py:105`, `src/vision.py:246`, `src/speech.py:118`, `src/association.py:40`.

Live recognition skips voice clustering. Across clips, identity is assigned by greedy overlap of the last face boxes, threshold 0.20. Movement can create a new identity; a different person occupying the same location can inherit one. There is no appearance embedding, motion prediction or persistent voice evidence.

Both modes begin with Whisper segment boundaries. Offline ECAPA assigns one embedding/voice to each segment; it does not discover a speaker change inside that segment. Live mode selects a face over the entire segment's duration. Rapid alternating speakers can therefore receive one attribution. The overlap handler resolves overlapping input events; it is not itself an overlapping-speech detector.

The active-speaker threshold is 0.20 with a 0.12 margin. A sole candidate can pass at 0.21 even though its speaking probability is low. No labelled calibration benchmark was found, so the appropriate replacement threshold remains unknown.

### 7. Repeated setup and serial work add avoidable latency — confirmed operations; costs unmeasured

References: `src/live.py:66`, `src/media.py:136`, `src/main.py:118`, `src/vision.py:66`, `src/light_asd.py:170`.

Each clip incurs temporary-file I/O, full media re-encoding, separate audio extraction, FFprobe calls, frame decoding and a newly created MediaPipe landmarker. Whisper is warmed up; Light-ASD is cached after its first use but is not included in startup warm-up. Light-ASD and MediaPipe use CPU. Installed Whisper defaults to CUDA if available, otherwise CPU; this app does not select Apple's MPS backend and explicitly disables fp16. No hardware-specific throughput measurement was performed.

## Evidence and limits

- Read every application module and all six test modules, plus configuration, plan, README and previous assessment. No `.codegraph/` exists.
- Ran `.venv/bin/python -m unittest -v`: all 26 tests passed. Import produced font-cache warnings; assertions completed successfully.
- Ran two isolated Node checks using extracted current UI functions: stale successful response produced zero transcript insertions; event end beyond sampled track coverage returned null.
- Existing live tests use mocked recognition and HTML string assertions. They even assert the presence of the latest-number guard without testing its interaction with server rejection. No real model accuracy, live throughput, camera movement or segmentation evaluation is covered.
- Historical `output/events.json`: 82 visible events, 120 face tracks. `output/improved/events.json`: 97 events, 79 visible and 18 uncertain, 121 tracks. These files lack sufficient provenance to attribute them to the current code/model. Their transcripts differ; they do not establish current word error rate or camera performance.
- No new camera/microphone capture, full inference benchmark or manually labelled ground truth was used. Noise, microphone selection and individual pronunciation remain possible contributors that source inspection cannot resolve.

## Repair order and acceptance evidence

1. Correct result lifecycle and preserve speech coverage under load. Add session IDs and capture timestamps, distinguish submitted from accepted/processed jobs, and avoid invalidating valid results on rejected uploads. Keeping only fresh video is reasonable, but a transcript needs continuous audio coverage.
2. Decouple current visual tracking from delayed speech recognition. Attach attribution to stable track IDs and update their current geometry continuously; keep spoken-time and arrival-time explicit.
3. Make transcription continuous with buffered audio/context, appropriate endpointing and overlap reconciliation; define provisional versus committed text and its source.
4. Give active-speaker inference actual consecutive frames at its intended temporal rate. Limit detector work separately from mouth-motion evidence. Measure each stage before choosing a larger speech model or hardware backend.
5. Implement person segmentation if the required visual is a silhouette; retain face-to-person association and handle occlusion explicitly.
6. Evaluate on a manually transcribed/labelled recording with motion, turn changes, off-screen speech and silence. Measure word error rate, dropped audio/results, median/tail caption delay, identity switches, wrong-person highlights and mask quality. Add asynchronous UI/service regression coverage for the confirmed defects.

A measured latency target must be agreed before model tuning. The existing defects can be addressed independently of that target.
